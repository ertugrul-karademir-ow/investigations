Lesson 4 · Workload identity · 12 minutes

Trace application-sa from Terraform to Pod

Your win: explain the complete identity chain and distinguish “who the Pod is” from “what it may do.”

One-sentence model: application-sa is a namespace-local Kubernetes ServiceAccount, federated to a dedicated Azure managed identity, that selected application Pods use for Service Bus, MongoDB Atlas, and optional Kubernetes API access.

1. Separate the two identities

IdentityLives inPurpose
application-saOne Kubernetes namespaceIdentifies a Pod to Kubernetes and supplies the token subject used by federation.
User-assigned managed identityMicrosoft Entra ID / AzureReceives Azure roles and represents the workload to external services.

The bridge is an OIDC federated credential. It trusts tokens from the AKS issuer only when the subject exactly matches system:serviceaccount:<namespace>:application-sa. The namespace is therefore part of the security boundary; an account with the same name in another namespace has a different subject.

2. Terraform decides which namespaces qualify

In application_identities.tf, Terraform computes two namespace sets and takes their union:

namespaces_with_dapr_enabled
mongo_workload_namespaces

application_workload_namespaces =
  namespaces_with_dapr_enabled ∪ mongo_workload_namespaces

A namespace qualifies when it needs Service Bus through Dapr, MongoDB Atlas, or both. For every qualifying namespace, Terraform creates a user-assigned managed identity and federated credential. It then adds only the permissions that namespace needs:

Namespace needTerraform result
Dapr enabledAssign the custom DAPR Service Bus role to the namespace's managed identity.
Atlas application accessCreate an Atlas workload user whose name includes that managed identity's client ID, with database roles and scopes from configuration.
BothOne managed identity receives both sets of permissions.

3. Terraform hands Kubernetes creation to Argo CD

Terraform does not directly create the ServiceAccount. In argocd_app_of_apps.tf, it adds these values to every qualifying application namespace:

applicationServiceAccount:
  enabled: true
  identityId: <managed identity client ID>
  tenantId: <Azure tenant ID>

The handoff is:

Terraformrenders app-of-apps values
Argo CDrenders cluster-namespaces
Namespace apprenders one namespace chart
Helmcreates application-sa

The namespace chart's application-service-account.yaml creates the account with the workload identity client-ID and tenant-ID annotations. If applicationServiceAccount.enabled is false, it renders nothing.

4. Deployment charts must explicitly select it

Creating a ServiceAccount does not make Pods use it. A Pod template must set spec.serviceAccountName: application-sa; otherwise Kubernetes selects the namespace's default ServiceAccount.

Latest product chartSelection behavior
Product SwitchingserviceAccountName defaults to application-sa; API, worker, and smoke-test workflow use it.
PricinguseApplicationServiceAccount defaults to false. When a layered values file enables it, API, worker, and adhoc-function Pods select the account.
AssortmentuseApplicationServiceAccount defaults to false. When enabled, analytics API, webtool API, and job API Pods select it.

Because the deployment repository uses layered Helm values, the chart default alone does not tell you what a live environment renders. Trace the product's ApplicationSet values order and the most specific client/environment override.

There is a second Pod opt-in. Azure workload identity also requires the Pod label azure.workload.identity/use: "true". Selecting the ServiceAccount establishes the Kubernetes identity; the label asks the AKS webhook to inject the projected token and Azure environment used for federation.

5. Follow the runtime token

Podselects application-sa
Webhookprojects a signed token
Entrachecks issuer, audience, subject
Identityreceives an access token
Servicechecks its permissions

The token does not contain a permanent Azure secret. Microsoft Entra accepts the short-lived Kubernetes token because the federated credential pre-authorizes its issuer and exact ServiceAccount subject. This is the flow described by the AKS workload identity documentation.

6. Keep the permission planes separate

Permission planeConfigured byExamples
External service accessAzure role assignments and Atlas workload usersManage Service Bus entities; read or write an Atlas database.
Kubernetes API accessKubernetes RoleBindings and ClusterRoleBindingsCreate Dask CRDs; optionally submit or manage Argo Workflows.

Product Switching binds Dask permissions to the same ServiceAccount. The namespace chart may also include it in the Argo Workflows API RoleBinding. These bindings do not grant Service Bus or Atlas access, and Azure roles do not grant Kubernetes API access.

Retrieval check

A Pod selects application-sa but lacks the workload-identity label. What is the likely result?

Diagnose one broken link at a time

  1. Did Terraform classify the namespace as Dapr-enabled or Atlas-enabled?
  2. Does the namespace contain an annotated application-sa?
  3. Does the rendered Pod select it?
  4. Does the Pod carry the workload-identity opt-in label?
  5. Does the federated credential subject exactly match the namespace and account name?
  6. Does the managed identity have the target service's permission?

Practice on the repositories

Choose one Product Switching environment. Trace its namespace into application_workload_namespaces, identify its managed identity and federated subject, follow the client and tenant IDs through the Argo CD values, then find every Pod or workflow selecting application-sa. Classify each permission you find as Kubernetes RBAC, Azure RBAC, or Atlas authorization. Compare your trace with the application ServiceAccount change map.
