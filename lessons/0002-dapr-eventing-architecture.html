Lesson 2 · Eventing architecture · 15 minutes

Follow an event through Dapr and Fabric

Your win: you will be able to separate what the application, Dapr, Azure Service Bus, Terraform, and Argo CD each own.

One-sentence model: applications speak Dapr's pub/sub API, a Dapr Component adapts those calls to Azure Service Bus, and Service Bus durably stores and fans out the messages.

1. Dapr is the adapter, not the broker

Publishercalls a local Dapr API
Dapr sidecarwraps and translates the event
Service Busstores it on a topic
Subscriptionselects a consumer copy
Dapr sidecarcalls the subscriber route

The publisher knows a Dapr component name and topic, not Service Bus credentials or a consumer address. The subscriber declares interest in a topic and a handler route. Dapr provides an at-least-once delivery model, so handlers must tolerate duplicate delivery. See Dapr's pub/sub overview.

2. Fabric has two event lanes

LaneBoundaryTypical flow
Compute eventsOne Service Bus namespace per client and event tierApplication-to-application pub/sub through Dapr
Data eventsOne Service Bus namespace per data environmentDatabricks ETL status event to an application subscriber

Compute tiers map to only three event tiers through default_events_tier: most short-lived tiers share testing, while staging and production use separate buses. This avoids a Service Bus namespace per application namespace while preserving the important environment boundaries.

3. How the compute lane is provisioned

Use DEV DMO as the concrete example. Cluster-level dapr_enabled = true enables the Dapr platform. A namespace such as assortment-latestcommit-dmo separately sets dapr_enabled = true. Its latestcommit compute tier maps to the testing event tier.

Opt indapr_enabled
Map tierdefault_events_tier
Create buscompute_events.tf
Create identityapplication_identities.tf
Install DaprArgo CD + Helm

compute_events.tf takes the distinct event tiers used by opted-in namespaces and creates one Service Bus namespace for each. The Service Bus module uses Standard SKU and denies traffic except listed AKS and corporate egress IPs.

Two gates are required: the cluster-level flag installs Dapr and enables identity wiring; the namespace-level flag opts in a workload. In the current Terraform, Service Bus tier discovery checks the namespace flag but not the cluster flag, so a bus can exist while the Dapr control plane and identities remain disabled.

4. Passwordless access: service account to Service Bus

For each compute event tier, Terraform creates one user-assigned managed identity and grants it the custom DAPR Service Bus role on that tier's Service Bus namespace. Every opted-in Kubernetes namespace receives a federated credential on that identity.

system:serviceaccount:assortment-latestcommit-dmo:dapr-enabled-sa
  → AKS OIDC federation
  → testing-tier managed identity
  → DAPR Service Bus role
  → rtls-dev-dmo-testing Service Bus namespace

The namespace Helm chart creates the annotated dapr-enabled-sa. The exact service-account name must match the federated credential's subject. The managed identity client ID is also saved as dapr-managed-identity-client-id in the environment Key Vault so a Dapr Component can resolve it without hard-coding.

5. Control plane, sidecars, and Components

Terraform hands values to the app-of-apps chart. Argo CD then installs the official Dapr Helm chart into dapr-system. That is the cluster-wide control plane.

The application deployment must still request a Dapr sidecar, use the expected service account, and provide a pub/sub Component of type pubsub.azure.servicebus.topics. The Component names the Service Bus namespace and authentication metadata. Subscriptions then connect topics to application routes.

This infrastructure repository does not contain the final Azure Service Bus pub/sub Component or application subscription manifests. Those belong to application/deployment configuration. Therefore, this repo proves that the platform and identity path exist—not that a particular topic contract or handler is wired correctly.

6. The separate data-event path

The data platform creates a Service Bus namespace per data environment and a fixed fabric-data-etl topic. Databricks receives a send-only topic connection string in the data Key Vault and publishes ETL events directly. For Dapr-enabled application namespaces linked by data_environment_key, Terraform creates separate data-event managed identities and federation.

Unlike compute identities, data-event identities are bucketed in groups of 20 namespaces to respect Azure's federated-credential limit. Compute event identities currently contain a TODO for the same limit.
