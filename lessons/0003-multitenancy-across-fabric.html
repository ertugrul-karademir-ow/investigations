Lesson 3 · Multitenancy · 20 minutes

Trace one tenant across five repositories

Your win: you will be able to review a tenant change end to end and identify where data could cross a retail-banner boundary.

One-sentence model: one product deployment may serve several retail subbrands, but every request or job carries a validated tenant key that selects tenant-specific authorization, configuration, queues, source-data scope, and MongoDB credentials.

1. What “tenant” means here

A tenant is normally a retail subbrand or banner inside a client deployment—not an Azure or Entra tenant. For example, one KFL Promo namespace can serve the klde and klsk banners. The tenant key is the application's stable routing key; bannerCode maps that tenant to its identity in the Fabric data platform.

This is a hybrid isolation model: infrastructure is shared at some outer layers, while databases and runtime context isolate the inner tenant boundary. Multitenancy therefore is not one feature or one filter. It is an unbroken chain.

Infrastructure creates the isolation capability

In KFL compute configuration, a namespace lists several mongo_databases_in_atlas_cluster entries. Assortment uses assortment-klde, assortment-klro, and common-assortment; Promo uses promo-klde, promo-klsk, and common-promo.

The shared-cluster database module creates a different Atlas user with readWrite scoped to one database, then stores a database-specific connection string in the namespace Key Vault. Atlas compute is shared; database authorization is not.

Deployments join names to secrets

The KFL values in Assortment and Promo declare tenant names, banner codes, and allowed identity groups. Their Helm charts render two important products:

tenant klde
  → Dynaconf tenant entry: multitenancy.tenants.klde
  → Kubernetes secret key: KLDE__MONGO_CONNECTION_STRING
  → Key Vault secret: {namespace}-assortment-klde-mongodbatlas-pe-connection-string

The same templates also wire COMMON__MONGO_CONNECTION_STRING to a product-specific common database. Naming it common-assortment, common-pricing, or common-promo prevents unrelated products sharing an Atlas cluster from accidentally sharing application state.

3. A request becomes tenant-scoped

Assortment, Pricing, and Promo implement the same core mechanism. The browser selects a tenant and sends x-rtls-tenant (the query parameter ?tenant=... is also supported). Middleware does not trust that selector by itself:

x-rtls-tenant: klde
  → tenant exists in configuration?
  → authenticated user has an allowed group?
  → set rtls_context.tenantKey
  → enter tenant's async context
  → activate tenant's Mongo connection

See the middleware in Assortment, Pricing, and Promo. An unknown or unauthorized tenant returns 403.

The header is a selector, not proof of authorization. Isolation depends on validating it against both configured tenants and the authenticated user's tenant list before any tenant-aware operation runs.

Node's AsyncLocalStorage wrapper keeps tenantKey attached to the current asynchronous request and simultaneously activates the matching Labskit Mongo connection. Repository code can ask for the active connection without passing a tenant argument through every function.

4. Configuration and analytics follow the same context

Tenant isolation is also behavioral. The shared Node config accessor and Python config accessor deep-merge a tenant's overrides over defaults while excluding other tenants and the reserved common key.

default configuration
       + klde overrides
       = effective configuration for this klde request

When Node submits analytics work, rtls_context crosses the process boundary. Python reconstructs it in a ContextVar-backed RtlsContext. Tenant-aware Mongo and Fabric-data access then resolve through that context. Scheduled work cannot rely on an HTTP header, so Helm generates per-tenant workflows and explicitly inserts tenantKey.

5. What differs among the product repositories

RepositoryTenant responsibility
rtls-assortmentRequest and analytics context, database selection, per-tenant configuration; KFL currently demonstrates klde/klro.
rtls-pricingThe same shared pattern, including propagated request/Dapr context, case normalization, tenant-prefixed Redis messages, and dedicated multitenant tests.
rtls-promo-v3The same pattern plus tenant-prefixed Bull queues and tenant-aware callbacks; KFL demonstrates klde/klsk.

The important similarity is architectural: all three products treat tenant context as ambient execution state and use it to choose configuration and persistence. Product-specific background work introduces extra places—queues, callbacks, workflows—where that state must be copied explicitly.

6. Review a tenant change as a five-part contract

QuestionFailure if missed
Does infrastructure create tenant and common DB credentials?Missing secret or over-broad database access
Do deployment values use the same tenant and database names?Secret lookup points at the wrong database
Do allowed groups map users to only intended tenants?Unauthorized tenant becomes selectable
Does every request, job, event, queue, and callback carry context?Work runs unscoped or under another tenant
Does code use tenant-aware config and connection accessors?Defaults or another connection leak across tenants
Fail closed: in multitenant mode, missing or unknown context should be an error. Falling back to a default database makes a missing tenant look successful and is therefore the dangerous behavior.
